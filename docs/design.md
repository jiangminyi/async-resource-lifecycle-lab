# 资源代际与并发设计

## 为什么分开“当前键”和“存活代际”

当前键字典只保存允许新请求加入的代际。存活集合还包含已经取消或关闭、但底层操作尚未结束的旧代际。因此同一键可以同时有一个新代际和若干等待清理的旧代际；每个代际的实例、完成任务和取消源互相独立。

如果只删除字典并忽略旧任务，提供器稍后完成就会泄漏。若把旧任务结果重新放回字典，则会污染新一轮请求。这里两种行为都不允许。

## 不变量

| 不变量 | 维护位置 |
| --- | --- |
| 一个代际的引用数 = 尚未完成的获取数 + 已授予未归还租约数 | AcquireAsync、finally、DropReference |
| 每个键至多存在一个可加入代际 | 状态锁下的字典插入与 DetachLocked |
| 失效代际不可再次成为当前代际 | Detached 只由 false 变为 true；结果发布不执行字典插入 |
| 释放必须等到加载结束、引用归零、取消分发结束 | ClaimCleanupLocked |
| 每个代际只能取得一次清理权 | CleanupClaimed 在状态锁内单向变化 |
| 排空必须等到所有提供器回调结束 | 先完成 Cleanup，再从存活集合移除 |

所有状态变更使用同一把短时锁，便于局部推理。提供器加载、释放和取消回调都在锁外执行。共享完成任务设置 RunContinuationsAsynchronously，避免调用方延续在持锁路径内重入。

## 线性化位置

- **加入加载**：锁内增加引用。底层加载只由创建该代际的请求启动一次。
- **获取成功**：等待完成之后再次持锁，重新检查请求取消、管理器关闭和代际状态，然后创建租约。请求在这里把“等待引用”转换成“租约引用”，不重复增加计数。
- **取消失败**：该请求的 finally 归还预留引用。其他请求继续持有自己的引用。
- **管理器关闭**：锁内设置关闭标志并摘除当前代际。成功授予早于此位置的租约仍然有效；之后的授予失败。
- **最后归还**：锁内摘除代际并领取清理权，随后在锁外调用提供器释放方法。

取消和完成恰好同时发生时，不要求取消总是获胜。获取成功位置之前观察到取消则失败；成功位置之后才取消则租约已经归调用方所有，必须显式归还。

## 取消源为什么也需要生命周期

取消请求可能触发用户提供器回调，回调又可能让底层加载完成。如果此时先清理代际并 Dispose 取消源，外层 Cancel 仍可能正在分发回调。

每个代际记录 CancellationDispatches。决定取消时在锁内增加，分发结束后在 finally 中减少；清理权必须等该计数归零。这样，关闭排空也不会早于取消回调的异常收集完成。

## 错误分层

- 加载异常传回该代际的所有等待者；失败代际不保留在缓存中，后续请求可以重试。
- 请求取消只使对应获取任务失败。
- 管理器关闭使未授予请求抛出 ObjectDisposedException。
- Release 或取消回调异常记录在排空结果中；WhenDrained 以 AggregateException 报告。已经尝试释放的实例不会被再次释放，以免重复副作用。
- 若加载失败之前已分配底层资源但未返回，清理由提供器负责。池只能拥有实际成功交付的实例。

## 取舍

单把锁让键映射、代际、引用和关闭状态具备统一顺序。它适合展示正确性，并非声称在高频资源调度中性能最优。尚未做锁争用或不同平台性能测量；没有公开吞吐或延迟数字。

不引入后台定时器、自动重试和缓存容量策略，是为了让加载失败、用户取消、资源归还和关闭的责任可以明确审计。后续扩展应先维持这些不变量，再补对应的竞争测试。
